# CRM «Чистый Липецк»

Бэкенд CRM департамента: мастер-данные (инженеры, участки, назначения, ведомства-исполнители,
типы нарушений), реестр контейнерных площадок, регистрация инженеров из MAX-бота и приём нарушений
из Data Gateway.
Контракт с DG повторяет `test_crm_drt` один в один: DG переключается на эту CRM сменой адреса
и токенов, без правок в коде DG.

Стек: FastAPI, SQLAlchemy 2, PostgreSQL (SQLite для разработки), Alembic.

**Регистрация инженера.** Бот присылает телефон, CRM ищет инженера по номеру (+7, 8, со скобками и
пробелами — всё приводится к E.164):

- `registered` — номер найден, MAX-аккаунт привязан;
- `already_registered` — этот MAX-аккаунт уже привязан к этому инженеру;
- `pending_review` — номера нет в базе, заявка ждёт диспетчера (`/api/v1/registrations`, resolve/reject);
- `rejected` — инженер отключён или заявку отклонил диспетчер;
- `conflict` — номер уже привязан к другому MAX-аккаунту или наоборот.

Повтор с тем же `Idempotency-Key` отдаёт сохранённый ответ, с тем же ключом и другими данными — 409.

**События.** Подписанный конверт сохраняется во входящие (202, повтор — 200 `duplicate`, то же id с
другим содержимым — 409), затем разбирается в дело `NEW`. Не сошлось со справочниками — у дела
причина по-русски (`reviewReason`), событие помечается `NEEDS_REVIEW`, исполнителя или тип
инспектор исправляет при подтверждении. Упавший разбор добирает фоновый проход.

**Маршрут дела** — тот же, что во фронте (`src/entities/incident/lib/workflow.ts`, `sla.ts`), ответ
в форме `IIncident`:

| Действие | Из статуса | В статус | Кто |
|---|---|---|---|
| `confirm` (срок 24/48/72/720 ч, можно сменить исполнителя и тип) | `NEW` | `IN_PROGRESS` | инспектор, диспетчер |
| `dismiss` (причина) | `NEW` | `CLOSED`, `FALSE_POSITIVE` | инспектор, диспетчер |
| `report` (фото после, время и место съёмки, комментарий) | `IN_PROGRESS` | `VERIFICATION` | мастер исполнителя |
| `approve` | `VERIFICATION` | `CLOSED`, `FIXED` | инспектор, диспетчер |
| `return` (что не так) | `VERIFICATION` | `IN_PROGRESS`, срок прежний | инспектор, диспетчер |
| `escalate` | `IN_PROGRESS`, срок истёк | `KNM_ESCALATION` | инспектор или фоновый проход раз в минуту |
| `act` | `KNM_ESCALATION` | без смены | инспектор, диспетчер |

Срок у портала губернатора (72 ч), прямого поручения (24 ч) и СЭД (720 ч) фиксирован, выбор инспектора
не действует. Место съёмки отчёта сверяется с местом нарушения: дальше 150 м — пометка в хронике.
Каждое действие пишется в хронику дела и в аудит. Ошибки — `{detail, message}`, как ждёт фронт.

**Контрольное мероприятие в document-service (этап 2).** При подтверждении дела CRM вызывает
внутренний API `POST /internal/crm/cases/sync`, создаёт или обновляет связанное мероприятие,
передаёт номер CRM, адрес, описание нарушения и дату фиксации. Связь повторно синхронизируется
без создания дублей. Ответ сохраняет статус и readiness в деле; эти сведения доступны в
`document_service` в списке и карточке даже до получения статуса, если уже есть связь с мероприятием
или диагностические данные. Инспектор может сохранить уточнённые поля через
`POST /api/v1/incidents/{id}/document-service/data`; каждый ответ синхронизации обновляет readiness
того же связанного дела, если сервис его возвращает, и сам по себе не формирует расширенный пакет.
Сервис проверяет готовность только документов `assignment` («Задание») и
`decision` («Решение»); если обязательные сведения или шаблон отсутствуют, CRM показывает список
недостающих полей и форму со списками из справочников document-service: вид контроля, форма и орган
контроля, контролируемое лицо, объект контроля, подписант, предмет мероприятия, тип основания и тип
пункта решения. Плановые начало и окончание мероприятия, реквизиты основания и текст пункта решения вводятся там же.
Полная карточка мероприятия остаётся доступна по ссылке. Сохранение повторяет проверку и формирует
два документа, когда проверка пройдена. Остальные документы первичного пакета этим действием не создаются.
Действие `act` продолжает первичный пакет; событие document-service с суффиксом `:extended` сохраняет
его ID и переданные коды/названия документов в `knmPackage` ответов списка и карточки. Событие не
передаёт readiness или URL файла, поэтому CRM не подставляет их: `downloadUrl` остаётся `null`, пока
сам пакетный ответ не предоставит допустимый путь к документу.

Для локальной разработки сначала запустите `document-service`, затем включите интеграцию в
`.env` CRM и в `.env` document-service (одно и то же значение токена в обоих файлах):

```dotenv
# chisto-crm-main/.env
CRM_DOCUMENT_SERVICE_URL=http://backend:8000
CRM_DOCUMENT_SERVICE_PUBLIC_URL=http://127.0.0.1:8000
CRM_DOCUMENT_SERVICE_TOKEN=<случайный секрет не короче 32 символов>

# document-service/.env
CRM_DOCUMENT_SERVICE_TOKEN=<тот же секрет>
```

Compose обоих проектов подключается к общей сети `chisto-document-service`. Пересоздайте контейнеры
после изменения `.env`, а в каталоге `document-service` примените новую миграцию:

```bash
docker compose exec backend alembic upgrade head
```

При подтверждении CRM ждёт ответ сервиса; если сервис недоступен, действие вернёт ошибку и его
можно повторить после восстановления связи.

**Справочники** при первом запуске заполняются из бота (`app/data/categories.json`,
agent_city_48_bot@78e3b62): 9 ведомств и 48 проблем. Удалить можно только запись, заведённую по ошибке:
если на неё ссылаются дела, назначения, пользователи или площадки, CRM ответит 409 — такую запись выключают.

**Роли:** `admin` (всё), `dispatcher`, `inspector` (ведут дела), `executor` и `uk_master` (видят дела только
своей организации и сдают по ним фотоотчёт), `manager`; свои роли собираются из прав `GET /api/v1/permissions`.
Исполнителю без организации (`executor_id`) аккаунт не заведётся. Отчёт по делу сдаёт только
организация, на которую дело назначено.

**Аккаунты.** У ДРТ аккаунт без организации: он видит все дела. У каждого ведомства свой аккаунт,
привязанный к организации. Завести разом ДРТ и все действующие ведомства (уже заведённые логины не трогаются):

```bash
docker compose exec crm python -m app.cli agency-accounts
```

Логин ведомства — его ключ из бота (`ddhib`, `nature_ministry`, `housing_inspection`…), пароли печатаются
один раз. Возможности аккаунта меняются ролями: `PATCH /api/v1/users/{id}`.
`GET /api/v1/auth/me` отдаёт пользователя и в форме фронта: `role` (`ADMIN`, `INSPECTOR`, `UK`),
`department`, `organizationName`.
У организации-исполнителя есть вид (`kind`), набор как во фронте: `UK`, `REG_OPERATOR`, `OMSU`, `DRT`,
`UPRAVA`, `MPR`, `GZHI`.
Смена пароля или отключение пользователя закрывает его сессии. Действия пишутся в `/api/v1/audit`.

## Запуск

```bash
python scripts/bootstrap_env.py          # .env со случайными секретами
docker compose up -d --build             # CRM + PostgreSQL, http://127.0.0.1:${CRM_HOST_PORT}
```

Пароль первого администратора — `CRM_ADMIN_PASSWORD` в `.env`. Демо-участки и демо-инженеры —
`CRM_SEED_DEMO=true` (только для стенда).

Без Docker:

```bash
python -m venv .venv && .venv/Scripts/pip install -e ".[dev]"
.venv/Scripts/uvicorn app.main:app --reload    # SQLite в data/crm.db
```

Миграции применяются при старте. Новая миграция после правки моделей:
`alembic revision --autogenerate -m "..."` (тест `test_migrations.py` упадёт, если её забыть).

## Консоль системного администратора

`/admin/` — то же, что «Региональный контур» тестовой CRM, только на нашем API и с правами ролей.
Страница без сборки (`app/admin_ui/`: `index.html`, `admin.css`, `admin.js`, свои шрифты Golos Text и
JetBrains Mono), входит по тому же логину, что и «Диспетчерская».

| Раздел | Что видно и что можно | Право |
|---|---|---|
| Обзор | инженеры с MAX и без, заявки из бота, события по статусам, дела и просрочка, состояние DG | `references.read` |
| События DG | каждое событие целиком: инженер, нарушение, место, файлы, дело, все поля канонической модели и исходный JSON | `events.read` |
| Дела | список по статусам, со ссылкой на событие; вести дела — в «Диспетчерской» | `cases.read` |
| Регистрации из бота | заявки, которые не нашлись по телефону: привязать MAX к инженеру или отклонить | `registrations.review` |
| Инженеры | телефон, email, **MAX user ID**, текущий участок; добавить, поставить на участок, отвязать MAX | `references.read`, правка `engineers.write` |
| Участки, назначения, исполнители, типы нарушений | справочники DG с правкой; удалить можно запись без ссылок, остальные выключают | `references.read`, правка `references.write` / `engineers.write` |
| Площадки КП | реестр с поиском; карточка: паспорт, контейнеры, ответственные, дела, внешние ID, история правок; завести, изменить, подтвердить на месте, удалить и восстановить | `references.read`, правка `references.write` |
| Пользователи, роли и права | логины, роли, организация, смена пароля; свои роли из списка прав | `users.manage` |
| Журнал действий | последние 500 записей аудита с поиском | `audit.read` |
| Data Gateway | статус сопряжения, адрес CRM для DG, что CRM отдаёт по контракту | `integration.manage` |

Первый администратор при запуске — роль `admin` «Системный администратор», логин `CRM_ADMIN_USERNAME`
(по умолчанию `admin`), пароль `CRM_ADMIN_PASSWORD` из `.env`. Диспетчеру ДРТ консоль открыта без
пользователей, ролей и DG; у аккаунтов ведомств справочников нет — консоль им закрыта.

## Реестр контейнерных площадок

По «Справочнику КП и ведению карточек». Код карточки `LP-000001` постоянный; ID ФГИС УТКО — внешний
ключ (`kp_external_id`), сырые записи источника — `kp_source_record`, каждое изменение поля —
`kp_change_log`. Одна правка — одна версия карточки. Удалённая карточка остаётся в истории и восстанавливается.

Загрузка из публичной карты ФГИС УТКО (выгрузка докачивает, повторный импорт идемпотентен):

```bash
python scripts/utko_harvest.py data/utko
docker compose exec crm python -m app.cli kp-import-utko /app/data/utko/details.jsonl --complete
```

- Поле, которое правили вручную или на месте, выгрузка не перезаписывает. Ранг источника:
  ФГИС УТКО < регоператор < ОМСУ < проверка на месте = вручную. Попытка пишется в историю как «не применено».
- Точку, сдвинутую источником дальше 30 м, CRM не переносит — карточка уходит «на проверку».
- Число площадок изменилось больше чем на 5 % — импорт отказывает (`--force`, если так и есть).
- `missing_in_source` ставится только с `--complete` (полная выгрузка без сбойных ячеек). Площадка
  вернулась в выгрузку — снова «не проверена».
- Новый ID УТКО привязывается к старой карточке (рядом, тот же адрес), только если прежнего ID
  этой карточки в выгрузке уже нет. Один номер реестра у двух площадок — обе «на проверку».
- Вывоз по правилу — региональный оператор, ответственный «не подтверждён», пока его не подтвердят.
- `kp-import-utko` сверяет выгрузку только с площадками своего округа (`--area`): площадки остальной
  области в «пропавшие» не попадают и «скачком» не считаются.

**Коды — по нумерации ГЖИ** (решение 15.10.2026: одна площадка — один код у CRM, бота и ГЖИ). ГЖИ прислала
выгрузку «код КП — utko_id» по всей области (CSV через `;`: `code;utko_id;registry_number;name;municipality;
settlement;address_raw;latitude;longitude;category;status`):

```bash
docker compose exec crm python -m app.cli kp-codes-gzhi /app/data/gzhi/codes.csv
```

- Площадка сопоставляется по GUID УТКО и получает код ГЖИ; смена кода пишется в историю карточки.
- Площадки, которых в реестре нет (Елец, районы), заводятся по строке выгрузки — без контейнеров и без
  ответственных: регоператор вне Липецка в справочнике не заведён. Выгрузка УТКО потом допишет карточку.
- Своя площадка, которой нет у ГЖИ, получает номер после последнего (15.10: LP-006854, LP-006855).
- Повтор кода или GUID в файле — выгрузка не применяется совсем. Повторный запуск ничего не меняет.
- Новые площадки из УТКО по-прежнему получают следующий свободный номер — кто выдаёт коды новым
  площадкам, ещё не договорились с ГЖИ.

**Привязка дела.** Дела о площадке (типы `ekoprom.*` и `housing_inspection.trash_inside_kp`) при разборе
события привязываются к ближайшей КП в радиусе 50 м: `nearest_single` или `nearest_multi`, если рядом
несколько, уверенность 0.75. Инспектор уточняет площадку руками (`PUT /api/v1/cases/{id}/kp`) — автоматика
её больше не трогает. После загрузки реестра старые дела привязывает `python -m app.cli kp-link-cases`.

## Проблемы из домовых чатов (ГЖИ)

Домовой ГЖИ разбирает домовые чаты в MAX и шлёт проблему на контейнерной площадке в DG
(`POST /adapters/domovoy/webhook`, контракт — `backend/adapters/domovoy/WEBHOOK.md` в data_gateway_48).
DG качает фото в MinIO и доставляет сюда тем же конвертом, что и события бота, с
`event_type = waste_site_problem` (схема `datagateway.waste_site_problem` 1.0, `app/schemas.py`).
Потребителя `chisto-crm` в DG нужно подписать на этот тип (`event_types`).

`app/problems.py`: одна проблема — одно дело (`external_key` = `domovoy:<problem_id>`), источник дела
`HOUSE_CHATS`. Первая ревизия заводит дело NEW без инженера и назначения; исполнитель — по названию
организации из подсказки источника, тип — по теме ЕДС (`EDS_THEME_TYPES`, пока одна тема «Вывоз ТКО»).
Что не нашлось — в расхождение, и подтвердить дело без исполнителя и типа нельзя. Площадка — по GUID
ФГИС УТКО (`kp_method = explicit`), без него — по точке, как у дел с обхода. Следующие ревизии дописывают
в хронику новые сообщения жителей с текстом и добавляют фото; устаревшая ревизия дело не трогает;
«решено» от жителей пишется в хронику, статус ведёт инспектор.

## Фото

DG отдаёт на снимок ссылку MinIO, которая живёт час, сам файл хранится в MinIO. CRM при приёме
события забирает снимки к себе (`data/files`, в compose — том `crm_files`) и отдаёт их по постоянному
адресу `/api/v1/incidents/{id}/media/{i}`. Видео и снимки, которые забрать не удалось, CRM отдаёт по
свежей ссылке DG (`GET {адрес DG}/api/v1/storage/object?key=`). Адрес DG берётся из сопряжения,
переопределить — `CRM_DG_MEDIA_URL`. Снимки дел, принятых до 0.6.0, добирает
`python -m app.cli media-cache`.

## Фронт «Диспетчерская»

CRM отдаёт собранный фронт (`Diywdan/cleanLipetsk`) с того же адреса, что и API: кука сессии
работает без CORS. Сборка кладётся в `web/` (в compose подключена к `/app/web`):

```bash
cd cleanLipetsk && npm run build:crm -- --outDir ../chisto-crm/web --emptyOutDir
```

`build:crm` берёт `VITE_API_URL=/api/v1` из `.env.crm`. В Git Bash путь `/api/v1` в переменной
окружения превращается в `C:/Program Files/Git/api/v1`, поэтому адрес лежит в файле.
Нет `web/index.html` — CRM отдаёт только API. Папка подхватывается при старте контейнера,
дальше файлы можно менять без перезапуска. Страницы и консоль идут с `Cache-Control: no-cache`, сборка
в `/assets/` (с хешем в имени) — с вечным кешем: после выкладки хватает обычной перезагрузки страницы.

Карта фронта читает файл тайлов `maps/lipetsk.pmtiles` (~130 МБ, OpenStreetMap по области, сборка
Protomaps). Он лежит отдельно от `web/`, в git его нет, сборка `build:crm` его не включает — выкладка фронта
файл не трогает. Как получить файл — README фронта, раздел «Карта». Нет папки `maps/` — `/maps` не подключается.

## Подключение к Data Gateway

CRM и DG на одной машине общаются по имени контейнера через сеть `plo_integrations`:

```bash
docker compose -f compose.yml -f compose.dg.yml up -d
```

В `.env` DG:

```
LOCAL_REFERENCES_ENABLED=false
CRM_REFERENCE_BASE_URL=http://chisto-crm:8000
ASSIGNMENT_BASE_URL=http://chisto-crm:8000
CRM_REGISTRATION_BASE_URL=http://chisto-crm:8000
CRM_REGISTRATION_PATH=/api/v1/integration/bot-users/registrations
CRM_READ_TOKEN=<CRM_DG_READ_TOKEN из .env CRM>
CRM_WRITE_TOKEN=<CRM_DG_WRITE_TOKEN из .env CRM>
```

Потом в UI DG «Подключить CRM»: адрес `http://chisto-crm:8000`, setup-токен — `CRM_DG_WRITE_TOKEN`.
DG сам пришлёт ключ подписи на `/configure`; статус сопряжения — `GET /api/v1/integration/datagateway`.

## Сборка в сети ЦОД

`pypi.org` там режется по имени хоста (остальной PyPI доступен), поэтому либо зеркало:

```bash
docker compose build --build-arg PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/
```

либо собрать образ у себя и перенести: `docker save chisto-crm:local | ssh <вм> docker load`.
