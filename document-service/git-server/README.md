# Git-сервер проекта

Здесь лежит конфигурация git-сервера, на котором живёт репозиторий проекта.
Это **Forgejo** — свободный self-hosted git с веб-интерфейсом (форк Gitea):
история, ветки, задачи, pull request'ы и права доступа, но на своём сервере,
а не на чужом хостинге.

## Адрес

```
https://82.202.140.51:8443/
```

Git живёт на своём порту 8443: nginx приложения принимает соединение и
завершает TLS (сертификат Let's Encrypt выпущен на IP-адрес сервера), а
запросы уходят в контейнер Forgejo. Отдельный порт удобнее общего 443: у git
свой origin, ссылки для клонирования короче, и браузер не считает страницы
git и CRM одним доверенным пространством.

Старые ссылки вида `https://82.202.140.51/git/...` переадресуются на новый
адрес (301) — закладки и уже отправленные ссылки продолжают работать.

Когда появится домен, git удобно вынести на отдельное имя (`git.домен`):
меняются только `ROOT_URL`/`DOMAIN` здесь и блок в `nginx/nginx.conf` — сам
Forgejo от адреса не зависит.

## Как устроено

| Что | Где |
|---|---|
| Конфигурация | этот каталог (`docker-compose.yml`) |
| Данные: репозитории, база, настройки | `/home/deploy/git/data` |
| Обратный прокси и TLS | `nginx/nginx.conf`, блок `listen 8443` |
| Сеть | та же docker-сеть, что у приложения, — иначе nginx не увидел бы git |

Отдельная база данных не заводится: репозиториев немного, поэтому Forgejo
хранит метаданные в SQLite рядом с репозиториями.

SSH для git намеренно выключен (`DISABLE_SSH`): клонирование и push идут по
HTTPS, а ssh-доступ к серверу остаётся только у администратора. Если понадобится
git по SSH, включается `START_SSH_SERVER` и публикуется отдельный порт.

Регистрация закрыта (`DISABLE_REGISTRATION`), репозитории не видны без входа
(`REQUIRE_SIGNIN_VIEW`) — новые учётные записи заводит администратор.

## Запуск и остановка

```bash
cd /home/deploy/document-service

# запустить
docker compose -f git-server/docker-compose.yml up -d

# состояние и логи
docker compose -f git-server/docker-compose.yml ps
docker compose -f git-server/docker-compose.yml logs --tail=50 forgejo

# остановить
docker compose -f git-server/docker-compose.yml down
```

## Как добавить коллегу

1. Войти администратором на `https://82.202.140.51:8443/`.
2. **Администрирование → Учётные записи → Создать учётную запись**: логин,
   почта, пароль.
3. Передать человеку логин и пароль. Дальше он работает по ссылке
   `https://82.202.140.51:8443/andrey/document-service`.
4. Для доступа по git из командной строки человек создаёт себе токен:
   **Настройки → Приложения → Создать токен** (права `repository: read/write`),
   и использует его как пароль при `git clone`/`git push`.

Пароль для git по HTTPS лучше не использовать — токен можно отозвать, не меняя
пароль учётной записи.

## Обновление Forgejo

```bash
cd /home/deploy/document-service

# 1. сделать резервную копию (см. ниже)
# 2. поменять версию в git-server/docker-compose.yml
docker compose -f git-server/docker-compose.yml pull
docker compose -f git-server/docker-compose.yml up -d
```

Forgejo сам выполняет миграции базы при запуске. Перед обновлением через
несколько мажорных версий резервная копия обязательна.

## Резервное копирование

Репозитории и метаданные лежат в `/home/deploy/git/data`. Проще всего держать
зеркало репозитория проекта рядом с остальными бэкапами:

```bash
git clone --mirror https://82.202.140.51:8443/andrey/document-service.git \
    /home/deploy/backups/document-service.git
```

Затем достаточно `git -C /home/deploy/backups/document-service.git remote update`
в `backup.sh` — зеркало подтянет новые ветки.

Данные самого Forgejo (`/home/deploy/git/data`) в бэкап не входят: они
восстанавливаются из зеркал репозиториев и заново заведённых учётных записей.
